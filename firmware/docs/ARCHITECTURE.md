# Робот-балансировщик: Wi-Fi телеметрия, тюнинг и управление

Архитектурный отчёт: прошивка ESP32 (Rust) + десктопное приложение на C#.

---

## 1. Что нужно получить

| Требование | Как решается |
|---|---|
| Трассировка и графики в реальном времени | UDP-поток телеметрии 50–200 Гц + кольцевой буфер и осциллограф в UI |
| Изменение всех параметров из UI | TCP-канал команд, JSON-строки, сохранение в NVS |
| Управление роботом | UDP-команды движения с watchdog-остановкой |
| Wi-Fi логин/пароль не вшиты в прошивку | Список сетей в NVS + SoftAP-портал + сид-конфиг на этапе сборки |
| Робот работает в гостях, где другой Wi-Fi | Несколько сохранённых сетей, выбор по результатам сканирования, автопортал при неудаче |

Дополнительная, но самая ценная цель: **уйти от прошивки кнопками**. На плате оборвана линия DTR→GPIO0, поэтому каждая прошивка требует ручного BOOT+EN. OTA по Wi-Fi убирает это навсегда — ценой одной последней ручной прошивки.

## 2. Общая схема

```
┌──────────────────── ESP32 ────────────────────┐
│  ядро 1 (реальное время)                      │
│    control loop 200 Гц ── IMU ── PD-контур    │
│    генерация шагов (аппаратно, LEDC+PCNT)     │
│         │ атомики (без блокировок)            │
│  ─────────────────────────────────────────    │
│  ядро 0 (сеть и сервис)                       │
│    Wi-Fi stack ── telemetry tx ── cmd server  │
│    OTA ── NVS ── SoftAP-портал                │
└───────────────────────────────────────────────┘
        │ UDP 5555 телеметрия/управление
        │ TCP 5556 параметры/конфиг/OTA
┌───────────────── C# приложение ───────────────┐
│  Transport → Protocol → TelemetryBus → VM → UI│
│  графики, тюнинг, запись сессий, геймпад      │
└───────────────────────────────────────────────┘
```

Главный принцип: **сеть никогда не влияет на балансировку**. Контур управления читает и пишет только атомики, как сейчас делает `telemetry.rs`. Пропала связь, отвалился Wi-Fi, завис UI — робот продолжает стоять.

## 3. Критичный момент: Wi-Fi ломает тайминг контура

Это главный архитектурный риск, и его надо решить до написания сетевого кода.

Сейчас расклад такой:

- задача шаговика крутится в busy-loop с приоритетом 10 на ядре 1 и фактически занимает ядро целиком;
- контур управления — это pthread с приоритетом 10 на ядре 0 (`CONFIG_PTHREAD_DEFAULT_CORE_0=y`).

Wi-Fi-стек ESP-IDF живёт на ядре 0 и имеет приоритеты вплоть до 23, то есть **выше контура управления**. Если ничего не менять, контур начнёт вытесняться сетевыми задачами, `dt` поплывёт, а на PD-регуляторе с `kd_gyro=300` джиттер сразу превращается в рывки колёс.

Предлагаемое решение:

1. **Перевести генерацию шагов на аппаратуру.** LEDC выдаёт на пин STEP прямоугольник нужной частоты (скорость = частота), PCNT считает импульсы вместо ручного счётчика шагов. Это освобождает ядро 1 почти полностью и заодно убирает дрожание периода шагов, которое сейчас даёт busy-wait.
2. **Перенести контур управления на ядро 1** и оставить ядро 0 целиком сети.
3. Оставить в телеметрии метрики `dt_us`/`loop_us` с максимумами — это уже есть и станет основным индикатором того, что сеть не мешает.

Альтернатива, если не хочется трогать шаговик: поднять приоритет контура выше Wi-Fi. Так делать не стоит — при потере пакетов Wi-Fi-стек начнёт голодать, и связь будет рваться.

Отдельно про питание: Wi-Fi даёт импульсы тока до ~300 мА. При слабом buck-преобразователе это просадки и brownout-ресеты прямо во время балансировки. В плане работ заложена проверка питания и конденсатор по 3.3 В.

## 4. Конфигурация Wi-Fi

### Почему не просто файл

Простой конфиг-файл на SPIFFS звучит удобно, но менять его можно только заливкой образа через `espflash`, то есть снова кнопками BOOT+EN. Для сценария «пришёл в гости» это неприемлемо. Поэтому конфиг хранится в NVS и правится без компьютера.

### Трёхуровневая схема

1. **Сид на этапе сборки.** Файл `wifi_seed.toml` (в `.gitignore`) с домашней сетью попадает в прошивку через `build.rs`. Нужен только для первого запуска на чистой плате.
2. **Список сетей в NVS.** До пяти записей `{ssid, psk, priority}`. Это основной источник. Правится из UI по TCP или через портал.
3. **SoftAP-портал.** Если ни одна известная сеть не найдена за 15 секунд, робот поднимает точку доступа `BalanceBot-Setup` и отдаёт HTML-форму на `192.168.4.1`: список найденных сетей, поле пароля, кнопка «Сохранить». После сохранения — переподключение без перезагрузки.

Логика подключения при старте: сканирование эфира → пересечение с сохранённым списком → выбор по приоритету, при равенстве по RSSI → подключение → при обрыве три попытки → портал. Балансировка всё это время работает.

Полезная мелочь: на плате есть светодиод GPIO2. Дать ему второй смысл — редкое мигание «нет Wi-Fi», частое «портал поднят», ровное свечение «связь есть и робот армлен».

## 5. Протокол обмена

Два канала с разными требованиями к надёжности.

### 5.1 UDP 5555 — телеметрия, обнаружение, управление

Быстро, без гарантий, потеря пакета не страшна.

**Обнаружение.** UI шлёт широковещательный `HELLO` на `255.255.255.255:5555`, робот отвечает `INFO` (имя, версия прошивки, IP, MAC, версия протокола). Так UI находит робота без ввода IP и без mDNS.

**Подписка.** `HELLO` одновременно является подпиской: робот запоминает адрес отправителя и начинает слать туда телеметрию. UI повторяет `HELLO` раз в секунду как keepalive; через 3 секунды тишины робот перестаёт слать. Это защищает от «стрельбы в пустоту», когда UI закрыли.

**Пакет телеметрии** — фиксированный бинарный layout, little-endian, 72 байта:

| Смещение | Тип | Поле |
|---|---|---|
| 0 | u32 | magic `0x314E4C42` («BLN1») |
| 4 | u8 | версия протокола |
| 5 | u8 | тип сообщения (1 = telemetry) |
| 6 | u16 | длина полезной части |
| 8 | u32 | порядковый номер |
| 12 | u32 | uptime, мс |
| 16 | u8 | состояние (idle / balancing / fallen) |
| 17 | u8 | флаги (Wi-Fi, OTA, авария) |
| 18 | u16 | счётчик ошибок IMU |
| 20 | f32 × 6 | angle, accel_angle, gyro, accel_mag, gyro_bias, trim |
| 44 | f32 × 5 | cmd, wheel_rate, term_p, term_lean, term_d |
| 64 | i32 | steps |
| 68 | u16 × 2 | dt_us, loop_us |

На 100 Гц это 7.2 КБ/с — для Wi-Fi незаметно. Частота настраивается из UI в диапазоне 10–200 Гц; по умолчанию 100 Гц как компромисс между детальностью графиков и нагрузкой.

**Команды движения** (тип 2): `f32 forward` и `f32 turn` в диапазоне −1…1 плюс порядковый номер. Watchdog: если команды не приходили 300 мс, цели обнуляются и робот просто балансирует на месте. Это обязательный элемент — иначе разрыв Wi-Fi означает робота, уезжающего в стену на полной скорости.

Поворот требует правки `stepper.rs`: сейчас оба мотора получают одну скорость, нужно раздельное `left_rate` / `right_rate` с общим ограничением ускорения.

### 5.2 TCP 5556 — параметры, конфиг, OTA

Редкие сообщения, нужна гарантия доставки. Формат — JSON-строки, по одной на строку (`\n` как разделитель). На ESP32 это `serde_json`, который отлично работает под `std`; на стороне C# — `System.Text.Json`. Протокол читаемый, отлаживается обычным telnet и легко расширяется без ломки совместимости.

```jsonc
// запросы
{"cmd":"info"}
{"cmd":"get_params"}
{"cmd":"set_params","ka":1400,"kd":320,"kp":0.001,"kv":0.0025,"lean":5}
{"cmd":"save_params"}          // зафиксировать в NVS
{"cmd":"reset_params"}         // вернуть зашитые по умолчанию
{"cmd":"arm"} {"cmd":"disarm"}
{"cmd":"get_wifi"}
{"cmd":"set_wifi","networks":[{"ssid":"home","psk":"...","priority":10}]}
{"cmd":"set_telemetry_rate","hz":100}
{"cmd":"reboot"}

// ответы
{"ok":true,"params":{...}}
{"ok":false,"error":"unknown param: kx"}
```

Важное правило: `set_params` меняет коэффициенты в оперативной памяти немедленно (как сейчас делает `tuning.rs`), а `save_params` фиксирует в NVS. Это позволяет крутить ручки без риска записать в память неудачную комбинацию, от которой робот падает при следующем включении.

## 6. OTA-обновление по Wi-Fi

Ради этого стоит затевать всё остальное.

Сейчас таблица разделов содержит единственный `factory` на 4 МБ. Для OTA нужна новая раскладка на те же 4 МБ:

| Раздел | Размер | Назначение |
|---|---|---|
| nvs | 24 КБ | Wi-Fi сети, параметры регулятора |
| otadata | 8 КБ | какой слот активен |
| phy_init | 4 КБ | калибровка радио |
| ota_0 | 1.7 МБ | слот A |
| ota_1 | 1.7 МБ | слот B |

Текущая прошивка занимает около 700 КБ, так что запас двукратный даже с Wi-Fi-стеком.

Процедура: UI открывает TCP-сессию, шлёт `ota_begin` с размером и контрольной суммой, затем бинарь чанками по 4 КБ, затем `ota_end`. Прошивка пишет в неактивный слот, проверяет SHA-256, переключает загрузочный раздел и перезагружается. Новая прошивка обязана в течение 30 секунд подтвердить работоспособность (`esp_ota_mark_app_valid_cancel_rollback`), иначе бутлоадер откатывается на предыдущий слот. Это защита от «залил битое — поехал за кнопками».

Запрет на OTA во время балансировки: робот должен быть в состоянии idle, иначе `{"ok":false,"error":"disarm first"}`.

Переход стоит **одной** ручной прошивки с кнопками — той, что меняет таблицу разделов. Дальше только по воздуху.

## 7. Структура прошивки

Новые модули поверх существующих:

```
src/
  main.rs          точка входа, раскладка задач по ядрам
  control.rs       PD-контур (есть)
  filter.rs        комплементарный фильтр (есть)
  mpu6050.rs       IMU (есть)
  stepper.rs       шаговики → переписать на LEDC + PCNT, раздельные колёса
  telemetry.rs     атомики состояния (есть, дополнить полями)
  tuning.rs        UART-тюнинг (есть, остаётся как аварийный канал)
  net/
    mod.rs         запуск сетевых задач
    wifi.rs        подключение, сканирование, переподключение
    provisioning.rs SoftAP + HTTP-форма
    discovery.rs   HELLO/INFO
    telemetry_tx.rs UDP-отправка с настраиваемой частотой
    command.rs     TCP-сервер JSON-команд
    ota.rs         приём образа, проверка, переключение слота
  storage/
    nvs.rs         параметры регулятора и список сетей
  params.rs        единый реестр настраиваемых величин
```

`params.rs` — ключевая абстракция. Сейчас коэффициенты размазаны: часть в `Gains`, часть в константах `main.rs` (пороги арминга, угол падения), часть в `stepper.rs` (максимальная скорость, микрошаг). Стоит собрать всё настраиваемое в один реестр с именем, значением, диапазоном и единицами измерения. Тогда UI сможет построить панель настроек автоматически, а не хардкодить список полей, и `get_params` будет отдавать и метаданные тоже.

## 8. Приложение на C#

### Стек

- .NET 8.
- **Avalonia 11** вместо WPF — тот же XAML и MVVM, но приложение запустится и не под Windows. Если кроссплатформенность не нужна, WPF тоже подойдёт, слой UI изолирован.
- **ScottPlot 5** для графиков: умеет стриминговые сигналы с миллионами точек и не проседает на 100 Гц.
- CommunityToolkit.Mvvm — привязки без рукописного `INotifyPropertyChanged`.

### Слои

```
BalanceBot.Protocol     структуры пакетов, сериализация, версии
BalanceBot.Link         UdpTelemetryClient, TcpCommandClient, Discovery
BalanceBot.Core         TelemetryBus (Channel + кольцевой буфер), Recorder
BalanceBot.App          ViewModels + Views
```

Разделение `Protocol` в отдельную сборку окупается: там же лежит генератор/парсер, который можно покрыть юнит-тестами без железа, подавая заранее записанные пакеты.

### Потоки и производительность

Приём в фоновом потоке пишет в `Channel<TelemetrySample>`, оттуда данные ложатся в кольцевой буфер на 60 секунд истории (при 100 Гц это 6000 отсчётов, копейки по памяти). **UI обновляется по таймеру 30–60 кадров в секунду, а не на каждый пакет** — иначе интерфейс захлёбывается. Это типичная ошибка в таких приложениях, и её лучше избежать сразу.

### Экраны

1. **Дашборд.** Осциллограф с выбором каналов (угол, гироскоп, cmd, позиция, составляющие P/lean/D), общая временная ось, пауза и прокрутка истории, курсоры для замера амплитуды и периода. Рядом индикаторы: состояние, RSSI, джиттер `dt`, ошибки IMU, uptime.
2. **Тюнинг.** Слайдеры и поля для всех параметров из реестра, отправка при отпускании слайдера, кнопки «Применить», «Сохранить в NVS», «Откатить». Профили настроек в JSON-файлах на диске.
3. **Управление.** Виртуальный джойстик, клавиши WASD, опционально геймпад. Крупная кнопка аварийного стопа и пробел как горячая клавиша.
4. **Wi-Fi.** Список сохранённых сетей, добавление и удаление, приоритеты.
5. **Записи.** Старт/стоп записи в CSV, список сессий, открытие записи в том же осциллографе для разбора падения.

## 9. Дополнительные функции, которые реально помогут настройке

Отсортированы по практической пользе для вашей текущей задачи — борьбы с автоколебаниями.

**Спектр колебаний (FFT) по углу и гироскопу.** Сейчас частоту раскачки приходится угадывать по логу, где телеметрия выводится раз в 200 мс и даёт алиасинг. Спектр сразу покажет, где именно сидит предельный цикл: в районе 2 Гц — это контур управления и надо трогать коэффициенты; в районе 20–40 Гц — это механический резонанс или вибрация шаговиков, и коэффициенты тут не помогут.

**Тест переходной характеристики.** Робот по команде подаёт короткий импульс наклона и записывает реакцию на полной частоте 200 Гц во внутренний буфер, затем отдаёт его в UI. По форме отклика видно перерегулирование и запас устойчивости, а подбор коэффициентов превращается из «покрутил и посмотрел» в измерение.

**Чёрный ящик падений.** Кольцевой буфер на 3 секунды в памяти ESP32; при срабатывании порога падения он замораживается и выгружается в UI. Разбирать причину падения по последним 3 секундам на 200 Гц несопоставимо проще, чем по обрывкам лога.

**Сравнение сессий.** Наложить две записи с разными коэффициентами на один график — самый честный способ понять, стало лучше или показалось.

Дальше по желанию: телеметрия напряжения батареи (делитель на ADC, предупреждение о просадке — заодно объяснит часть загадочных падений), ультразвуковой датчик HC-SR04 из набора для остановки перед препятствием, запись и воспроизведение маршрутов.

## 10. Порядок работ

| Этап | Содержание | Результат |
|---|---|---|
| 0 | Новая таблица разделов + OTA + Wi-Fi подключение | Последняя прошивка кнопками, дальше по воздуху |
| 1 | LEDC+PCNT для шаговиков, контур на ядро 1 | Контур не боится сетевой нагрузки |
| 2 | UDP-телеметрия + discovery, минимальный C# с одним графиком | Видно, что происходит с роботом |
| 3 | `params.rs` + TCP-команды + панель тюнинга | Настройка мышкой вместо терминала |
| 4 | Раздельное управление колёсами, команды движения, watchdog | Робот ездит |
| 5 | SoftAP-портал | Работает в гостях |
| 6 | FFT, тест отклика, чёрный ящик, записи | Инструменты для точной настройки |

Этапы 0 и 1 стоит делать вместе и проверить джиттер до того, как появится сетевой код: если `dt` поплывёт потом, искать причину среди десятка новых модулей будет заметно сложнее.

## 11. Риски

| Риск | Проявление | Что делать |
|---|---|---|
| Wi-Fi вытесняет контур управления | Рост `max_dt_us`, рывки колёс | Этап 1 до сетевого кода, контроль джиттера в телеметрии |
| Просадки питания от радио | Случайные перезагрузки | Проверить buck, конденсатор по 3.3 В, телеметрия напряжения |
| Разрыв связи при езде | Робот уезжает | Watchdog 300 мс на команды движения |
| Неудачная прошивка по воздуху | Робот не загружается | Двойной слот + откат бутлоадером, подтверждение работоспособности |
| Плохие коэффициенты в NVS | Падает сразу после включения | Разделение «применить» и «сохранить», команда сброса к зашитым значениям |
| Помехи от шаговиков на I2C | Всплески `imu_errors` | Экранирование, короткие провода, подтяжки I2C |

## 12. Что решается попутно

- Прошивка перестаёт зависеть от кнопок BOOT/EN.
- Настройка перестаёт требовать перезагрузок и терминала.
- Появляются данные на полной частоте 200 Гц вместо выборки раз в 200 мс, на которой сейчас не видно настоящей формы колебаний.
- Параметры переживают перезагрузку, а не теряются вместе с сессией.
